## 卡:AR06-T05 — Bulk import 单槽 admission

- **验收标准(TASKS 原文)**:依赖:AR05-T03、AR06-T01。文件:`routes/projects.rs`、App admission state、相邻 tests。RED:两个 pending archive import 同时进入,或超预算/panic 后 slot 不释放。GREEN:读取大 body 前 admission=1;所有路径释放并 cleanup。验证:`bun cargo test -p koharu-rpc import_admission`。
- **现状(RED-0 源码实证)**:`import_project`(projects.rs:196)以 `body: Bytes` extractor 收参——axum 在 handler 运行前已把整个归档 body 缓冲进内存;无任何 import admission;两个并发大导入会各自缓冲完整 body 并同时进入 sanitize/spawn_blocking。既有槽位模式:`app.pipeline_slots`(per-project DashMap,AR06-T03)、`app.ai_slots`(全局 Semaphore(2),AR06-T04),均 RAII `OwnedSemaphorePermit`;pipeline 路由 429+Retry-After 构造在 pipelines.rs:118-130;import 路由 body 限值由 `tiered_body_limit` 中间件(api.rs:72-81,512 MiB)以 `DefaultBodyLimit` extension 注入。
- **设计**:
  - app.rs:`pub import_slots: Arc<tokio::sync::Semaphore>`,初始化为 1(全局单槽,与 ai_slots 同型)
  - projects.rs:`try_acquire_import_slot(app: &koharu_app::App) -> Result<OwnedSemaphorePermit, ApiError>`(429 文案 "import slot busy: another archive import is in flight")
  - 路由改签:`import_project(State(app), request: Request) -> ApiResult<Response>`:先取槽(busy → 429+Retry-After 响应,按 pipelines.rs:124-126 模式),再 `Bytes::from_request(request, &state)`(保留中间件注入的 512 MiB DefaultBodyLimit 语义)→ 既有 empty 检查/sanitize/publish/open_project;permit 持有至 handler 结束,所有路径(超预算/损坏/panic)经 RAII drop 释放
  - panic 释放:RAII permit drop 覆盖 spawn_blocking panic(JoinError 到达时 permit 已 drop),以 permit-drop 测试锁定(AR06-T03 同型先例)
- **RED 断言**(`bun cargo test -p koharu-rpc import_admission`):
  1. `import_admission_second_concurrent_gets_429` — 直接持有 import_slots 后调用路由(合法小归档)→ 429 + Retry-After "1";当前无槽位/无此响应 → FAIL(编译期脚手架:槽位存在但路由不取)
  2. `import_admission_slot_released_after_budget_rejection` — 超预算伪造归档导入失败(T02 per-entry budget)→ `try_acquire_import_slot` 立即成功(槽已释放);当前无槽位 → FAIL
  3. `import_admission_slot_released_on_permit_drop` — 取槽→drop→再取成功(RAII/panic 等价锁,AR06-T03 同型)
